# Spring Boot Logbook Request/Response Logging Example

A teaching catalog for [Zalando Logbook](https://github.com/zalando/logbook)
in Spring Boot: HTTP request/response logging that lives entirely in
configuration, with per-profile filtering strategies and field/header
obfuscation.

Spring Boot 4.1.1 · Java 25 · Logbook 4.2.0

## Running

```bash
cd logbook-logging-requests
./mvnw spring-boot:run
```

The app starts on port `8085`. With **no profile active**,
`logbook.filter.enabled=false` (see `application.yaml`), so Logbook logs
nothing at all - this is the safe-by-default state. Pass a profile to turn
logging on:

```bash
./mvnw spring-boot:run -Dspring-boot.run.profiles=dev
./mvnw spring-boot:run -Dspring-boot.run.profiles=prod
```

Real output for every scenario below (HTTP request/response + the exact
Logbook console lines produced) is captured in
[`sample-output.txt`](sample-output.txt) - generated by actually running the
app under each profile and calling each endpoint with curl, not hand-written.

## Endpoint catalog

| Endpoint | Technique demonstrated |
|---|---|
| `POST /api/logbook/echo` | Baseline: a plain, non-sensitive request/response, unobfuscated |
| `POST /api/logbook/sensitive` | `logbook.obfuscate.headers` (`Authorization`) + `logbook.obfuscate.json-body-fields` (`password`/`apiKey`/`token`) |
| `GET /api/logbook/status/{code}` | Trigger any response status on demand, to see filtering strategies decide whether Logbook logs the call at all |
| `POST /api/logbook/large` | A body bigger than `logbook.write.max-body-size` gets truncated in the **logged** copy only |

## Profiles: what each one turns on

| Profile | `logbook.filter.enabled` | Strategy | What gets logged |
|---|---|---|---|
| *(none)* | `false` (default) | - | Nothing, ever. Safe default for an unconfigured environment. |
| `dev` | `true` | none | Every request/response, regardless of status. `org.zalando.logbook: TRACE` is also set here - Logbook's writer logs at TRACE, so without raising the level it stays silent even with the filter enabled. |
| `prod` | `true` | `status-at-least`, `minimum-status: 500` | Only requests whose **response** is 5xx. Routine 2xx/4xx traffic produces zero log output. |

No Java code changes between these - toggling logging on/off, and choosing
what to log, is entirely `application-{profile}.yaml`.

## Obfuscation: headers and body fields

`application.yaml` configures:

```yaml
logbook:
  obfuscate:
    headers:
      - Authorization
      - Cookie
      - Set-Cookie
    json-body-fields:
      - password
      - token
      - secret
      - apiKey
```

Hitting `/api/logbook/sensitive` with an `Authorization` header and a body
containing `password`, `apiKey`, and `token` produces a logged request where
all four are replaced with `XXX` - but `username` (not on the list) is
untouched:

```
Authorization: XXX
...
{"username":"demo-user","password":"XXX","apiKey":"XXX","token":"XXX"}
```

`json-body-fields` matches by field name **anywhere in the JSON tree**, on
the raw request/response body text - a field the DTO itself ignores (or
doesn't even declare) is still masked, because Logbook obfuscates before the
body ever reaches Jackson/your controller. See `sample-output.txt`, section 2,
for the full real capture (`LogbookController.sensitive`).

## Filtering strategies: dev vs. prod

In `dev`, calling `/api/logbook/status/201` and `/api/logbook/status/500`
both produce a full request+response log entry - `application-dev.yaml` only
flips `logbook.filter.enabled`, it sets no strategy.

In `prod`, `application-prod.yaml` adds:

```yaml
logbook:
  strategy: status-at-least
  minimum-status: 500
```

Calling `/status/201` or `/status/404` now produces **zero** log lines - not
even a partial "Incoming Request" entry - while `/status/500` and
`/status/503` produce the usual full pair. Logbook has to see the response
before it can decide, so it holds the correlated request+response together
and only emits both once the response qualifies. This is what keeps a
production log from filling up with routine traffic while still guaranteeing
every server error has a complete record. See `sample-output.txt`, section 5,
for the real byte-for-byte proof (`LogbookProdProfileLoggingTest`).

## Body truncation

```yaml
logbook:
  write:
    max-body-size: 4096
```

Sending a 6000-character body to `/api/logbook/large` still returns
`"received 6000 chars"` - the controller gets the whole thing. Only the
**logged** copy is capped: the real captured log line is exactly
`4096 + 3` characters (`4099`), the extra 3 being the literal `"..."` Logbook
appends after truncating. See `sample-output.txt`, section 4, and
`LogbookDevProfileLoggingTest.bodyLargerThanMaxBodySizeIsTruncatedInTheLoggedRequest`.

## Excluded paths

```yaml
logbook:
  predicate:
    exclude:
      - path: /actuator/**
      - path: /v3/api-docs/**
      - path: /swagger-ui/**
      - path: /swagger-ui.html
```

Infrastructure/documentation endpoints never reach Logbook at all, in any
profile - there's nothing interesting to correlate a request ID against for
a liveness probe.

## Tests

```bash
./mvnw test
```

7 tests, real Logbook TRACE output captured via a `ListAppender`
(`LogCapture`) on the `org.zalando.logbook.Logbook` logger - no mocking of
Logbook itself:

- `LogbookControllerTest` *(no active profile)* — functional correctness of
  `echo`/`status`, and confirms the filter-disabled default produces zero
  Logbook log lines
- `LogbookDevProfileLoggingTest` *(`dev` profile)* — `Authorization` header
  and `password`/`apiKey`/`token` body fields obfuscated to `XXX` while
  `username` is untouched; a body over `max-body-size` is truncated to
  exactly `4096 + 3` characters in the logged request
- `LogbookProdProfileLoggingTest` *(`prod` profile)* — only responses at or
  above `minimum-status` produce any Logbook output; lower-status calls
  leave no trace at all
- `LogbookLoggingRequestsApplicationTests` — context loads

Each `@ActiveProfiles` combination loads its own Spring context (three
total), since `logbook.filter.enabled` and the strategy are read once at
startup.

## Deliberate simplifications

- **`spring.mvc.problemdetails.enabled=true` handles validation errors** —
  there's no custom `@RestControllerAdvice` in this module; a blank `text`/
  `message` on `/echo` or `/large` returns Spring's built-in RFC 9457
  `ProblemDetail`, which is enough for this catalog's purposes.
- **No log aggregation backend.** Logbook's `http` format style produces
  human-readable multi-line output for this demo; a real deployment would
  typically pair it with a JSON `Sink`/formatter and ship to a log pipeline.
- **`status-at-least` is the only strategy shown.** Logbook also ships a
  `body-and-status-at-least` strategy and supports fully custom
  `Strategy`/`Predicate` beans; those aren't needed to demonstrate the
  core idea here.
