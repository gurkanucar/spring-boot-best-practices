logbook-logging-requests - sample run output
==============================================
Captured by actually running the app under each profile and calling every
endpoint with curl. Console lines are Logbook's own TRACE output (via
org.zalando.logbook.Logbook), shown exactly as produced - not hand-written.


0) No active profile (application.yaml defaults: logbook.filter.enabled=false)
--------------------------------------------------------------------------------
Request:
  POST /api/logbook/echo  {"message":"no profile"}

Response:
  {"message":"no profile","length":10}

Console:
  (nothing - zero lines mentioning org.zalando.logbook, confirmed by grep)

  Note: this is the whole point of logbook.filter.enabled=false as the
  default - Logbook is wired into the filter chain but produces no output
  at all until a profile (dev/prod) turns it on.

4) --spring.profiles.active=dev - POST /api/logbook/large (6000-char body)
------------------------------------------------------------------------------
Request:
  POST /api/logbook/large  {"text":"xxx...(6000 x's)...xxx"}   (Content-Length: 6011)

Response:
  {"result":"received 6000 chars"}

Console (request body line, real capture, shortened here for readability):
  {"text":"xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx...(4093 more x's)...xxx"...

  Real measured facts (verified byte-for-byte on the actual log line):
    - full logged body length: 4099 characters
    - last 3 characters: "..."
    - 4099 = logbook.write.max-body-size (4096) + 3 ("...")

  Note: Logbook truncates the LOGGED copy of the body at max-body-size and
  appends "..." - the controller itself still receives and processes the
  full 6000-character body ("received 6000 chars" in the response proves
  it). Truncation only affects what ends up in the log.


5) --spring.profiles.active=prod - GET /status/{201,404,500,503}
----------------------------------------------------------------------
Requests (in order): /status/201, /status/404, /status/500, /status/503
All four return their requested HTTP status normally to the client.

Console: only 2 "Incoming Request" lines appear (verified by grep -c), for
exactly the 500 and 503 calls - 201 and 404 produce ZERO log output, not
even a partial/incomplete entry:

  TRACE ... org.zalando.logbook.Logbook  : Incoming Request: cd1315ceff808d7d
  Remote: 0:0:0:0:0:0:0:1
  GET http://localhost:8085/api/logbook/status/500 HTTP/1.1
  ...

  TRACE ... org.zalando.logbook.Logbook  : Incoming Request: a00e2262f66ef99a
  Remote: 0:0:0:0:0:0:0:1
  GET http://localhost:8085/api/logbook/status/503 HTTP/1.1
  ...

  Note: application-prod.yaml sets logbook.strategy=status-at-least and
  logbook.minimum-status=500. Logbook must see the response before it can
  decide whether to log - so it holds the request/response pair together
  and only emits BOTH (request + response) once the status turns out to
  qualify. A 201 or 404 leaves no trace anywhere, by design: this is what
  keeps a production log from filling up with routine 2xx/4xx traffic
  while still guaranteeing every 5xx has a full request+response record.
